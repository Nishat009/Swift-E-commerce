# SwiftCart security overview

SwiftCart is the fashion e-commerce shop in this repository: a Next.js 16 storefront and admin panel
(repo root) backed by an Express + MongoDB API (`backend/`). This page shows how every request that
changes data is authorized, and how that is verified. The route table at the end is generated from
the routers themselves and checked by a test, so it cannot drift from the code.

## How a request is authorized

| Guard | Where | What it does |
| :--- | :--- | :--- |
| `protect` | [authMiddleware.js:21](backend/src/middleware/authMiddleware.js#L21) | Requires a valid access token (15 min JWT) whose `tokenVersion` still matches the user; otherwise 401 |
| `authorize('admin')` | [roleMiddleware.js:4](backend/src/middleware/roleMiddleware.js#L4) | Requires the `admin` role; otherwise 403 |
| `requireSuperAdmin` | [roleMiddleware.js:34](backend/src/middleware/roleMiddleware.js#L34) | Refunds, status overrides, wallet adjustments, payment settings: a real (non-demo) admin, optionally limited to `SUPER_ADMIN_EMAILS` |
| `blockDemoAdmin` | [demoAuthController.js:83](backend/src/controllers/demoAuthController.js#L83) | The shared one-click demo admin cannot change roles, delete users, change order status, read or send customer emails, export statements or test gateways |
| Demo privacy | [demoPrivacy.js:52](backend/src/middleware/demoPrivacy.js#L52) | Everything sent to the demo admin has customer emails, phones, street addresses, IPs and surnames masked |

**Ownership.** Signed-in routes act only on the caller's own records. Cart, wishlist, wardrobe and
notifications query by `user: req.user.id`. Orders are checked against the owner (view, cancel,
return, refund offer: [orderController.js:178](backend/src/controllers/orderController.js#L178),
[:199](backend/src/controllers/orderController.js#L199), [:420](backend/src/controllers/orderController.js#L420),
[:645](backend/src/controllers/orderController.js#L645)). Starting a payment looks the order up by id
and owner in one query ([paymentController.js:23](backend/src/controllers/paymentController.js#L23)).
Reviews can be edited or deleted only by their author or an admin
([reviewController.js:144](backend/src/controllers/reviewController.js#L144), [:177](backend/src/controllers/reviewController.js#L177)).
Another customer's record answers 404 or 403.

**Public routes** (sign-in, contact form, newsletter, chat, back-in-stock alerts) are deliberate. Each
is rate-limited ([config/rateLimits.js](backend/src/config/rateLimits.js)); the Stripe webhook is
accepted only with a valid signature ([paymentService.js:160](backend/src/services/paymentService.js#L160)),
and gateway returns never trust the URL: the server asks the gateway and checks the paid amount
([paymentService.js:217](backend/src/services/paymentService.js#L217)).

**Sessions.** The refresh cookie (httpOnly) is backed by a server-side session that stores only a
SHA-256 of a one-time secret, rotates on every refresh, is revoked on logout, and on replay of an old
token revokes all of the user's sessions and access tokens
([refreshSessions.js:59](backend/src/services/refreshSessions.js#L59)).

## How it is verified

```bash
npm --prefix backend test            # 75+ tests, including:
npm --prefix backend run test:routes # only the route-guard policy check below
```

- [backend/tests/route-guards.test.js](backend/tests/route-guards.test.js) walks every router and fails if
  a POST/PUT/PATCH/DELETE route lacks `protect`, lacks `authorize('admin')` without being on the public or
  signed-in list in [routePolicy.js](backend/src/config/routePolicy.js), or if the table below is out of date.
- [backend/tests/security.test.js](backend/tests/security.test.js) calls the API: guests and customers get
  401/403 on admin routes, drafts stay hidden, another customer's order cannot be paid, demo admin limits
  and masking, refresh rotation, logout revocation and replay detection.
